## 1. История checkpoint нарушает интерпретацию новых withheld-масок в Q2

**Источник:** `repo/iclr/research.py:125–137`, `repo/evidence/upgrade/previous_q06.json`, исходные `reference_data/train.jsonl` и маски v2.

Q2 берёт исторический composition seed0 checkpoint, а по умолчанию работает с mask1. Его старое supervised-обучение исключало original-маску, не mask1/mask2. Пары обеих новых масок встречаются в историческом train-пуле.

Для mask1 в исходном пуле witness-последовательностей: SC2→REV — 506 вхождений, SC2→SC2 — 599, SH1→SC2 — 462. Реконструкция неизменённой функцией `mixture` с конфигом historical composition seed0 (5000 предъявлений, replay 20%, 2 эпохи, fixed witness) даёт соответственно 391, 467 и 384 вхождения за эпоху. Это реконструкция по сохранённым данным/конфигу, не независимая проверка старого фактического training stream.

**Следствие:** Q2 остаётся допустимой диагностикой reward-обновлений после SFT. Но B/D этой ветки нельзя называть композициями, никогда не встречавшимися модели на предыдущих этапах. Отсутствие совпадающих задач/состояний не исключает знакомства с парами операций.

**Исправление:** либо явно ограничить вывод «held out only from this continuation», либо использовать matching-mask SFT initialization, либо начать первичную диагностику с original-маски. Для утверждения о переносе на новые пары при нескольких масках потребуется соответствующая история инициализации для каждой маски. Добавить exposure ledger по всем этапам, не только текущему train. Старый checkpoint также видел depth4, что отдельно ограничивает length-transfer интерпретацию Q2.

Это уточнение относится и к ранее предложенному плану использовать замороженный SFT checkpoint: его история должна соответствовать проверяемому виду переноса.

## 2. Primary metric не проверяет совместное использование START и TARGET

**Источник:** `repo/plans/research_v3.json:primary`; `repo/iclr/research_analysis.py:34–35`; `repo/iclr/research_evaluate.py:24–50`.

Primary — local pair accuracy на four-TARGET панелях. `compare` действительно фильтрует `kind == 'four_target'`. Crossed interaction и joint accuracy рассчитываются, но остаются вторичными и не входят в этот paired analysis.

Four-TARGET — полезная проверка против фиксированного program prior, но TARGET-only scoring может пройти её. Математический контрпример: four-TARGET score matrix с единицами на диагонали и нулями вне её даёт pair accuracy 1. На crossed-панели TARGET-only scores `[[1,0],[0,1],[1,0],[0,1]]` дают interaction 0, cell accuracy 0.5, joint accuracy 0.

**Исправление:** до запусков уточнить основное утверждение и правило успеха. Для тезиса «совместное использование START/TARGET улучшилось» обязательны paired crossed cell/joint результаты; для тезиса «метод лучше решает задачи» нужны raw full-candidate H1/H8/correct mass на обычных задачах. Рост одной pair accuracy допустим как более узкий результат, но не заменяет эти выводы. Анализ crossed/обычных метрик нужно добавить до final freeze. Новые non-smoke crossed-панели существуют, поэтому fallback их отсутствием здесь не требуется.

Если вводятся несколько подтверждающих статистических тестов, заранее определить их иерархию/правило множественных проверок. Не выбирать удобный endpoint после final.

## 3. MC gate смешивает редкость положительных ответов с численной неисправностью

**Источник:** `repo/iclr/research_gradient.py:103–118,132–147`.

Допуск проверяет `||MC_mean - exact|| <= 4 * estimated_SE + 1e-7`. Когда во всех sampled-группах ответы неверны, все sampled-градиенты и эмпирическая SE нулевые. Точный ожидаемый градиент при этом может быть ненулевым.

Гипотетический пример, не результат Qwen3: масса правильных программ m=1e-6, G=32, 128 групп. Вероятность не увидеть ни одного правильного ответа — около 99.59%. Для двухпрограммного softmax норма точного ожидаемого градиента около 7.87e-6, поэтому действующий gate при такой реализации выборки не проходит.

**Следствие:** ветка может быть закрыта именно в интересующем режиме дефицита sampled-сигнала; это не обязательно ошибка ядра.

**Исправление:** отдельные статусы для численной корректности ядра и достаточности MC-выборки; например `kernel_ok`, `mc_inconclusive_rare_reward`, `optimizer_check_failed`. В редком режиме использовать заранее ограниченное увеличение MC-бюджета либо точную/условную проверку ожидания с корректным взвешиванием. Диагностическое изменение sampling не должно молча менять on-policy training objective. Дополнительно сравнивать train-диагностику на том же типе данных, что и training pilot: сейчас первая берёт первые четыре строки `train.jsonl`, второй — `manifest['training_panels']`.

## 4. Внешний DSL пока смешивает композиционность и переобучение смыслов операций

**Источник:** `repo/iclr/research_dsl.py:16–39`; `repo/iclr/research.py:101–139`.

Внешняя ветка наследует polynomial atomic checkpoint, но OP0–OP4 получают новые значения. OP1/SC2 становится возведением первого элемента в квадрат, OP3/AC1 — сортировкой, OP4/AX1 — циклическим сдвигом. Добавить определения в prompt полезно, но это не устанавливает предварительное владение этими примитивами.

**Следствие:** это допустимый опыт переноса/адаптации метода в новый домен. Но это ещё не чистый тест композиции предварительно освоенных навыков.

**Исправление для такого тезиса:** общая list-DSL atomic warm-up на разрешённых train-полях, проверка атомарных навыков, затем одинаковый checkpoint → baseline/selected method. Для переноса между полями не включать withheld поля в warm-up. Не подменять этот небольшой авторский DSL результатом опубликованного benchmark.

## 5. Размер pilot и статистические границы

64 train-панели — это 256 разных задач. При epochs=2 и panel_batch=1 получаются 128 supervised updates, 512 предъявлений и 1536 supervised operation-token labels. CF/entropy добавляют свои сигналы; число operation-token labels не описывает всю вычислительную стоимость.

Это разумный screening-бюджет, но отрицательный результат не доказывает бесполезность CF/entropy. Для перспективной пары полезна короткая заранее заданная dev-кривая бюджета. В crossed final по 16 панелей на семью; интервал должен отражать эти панели, а не 64 клетки как независимые наблюдения. Conditional panel-bootstrap в коде честно ограничен выбранными checkpoint/масками и не оценивает вариативность новых atomic initializations.

На training-панелях решение уникально: условная энтропия правильного множества там равна нулю. Выводы о разнообразии нескольких правильных решений должны опираться на обычные задачи с несколькими решениями, не на эти train-панели.

## Практический порядок

1. До начала научной серии уточнить scope Q2 и endpoint/правило успеха, выпустить новую явную версию протокола/lock. Не переписывать старые результаты.
2. При двух GPU начать Q1 на q06 и Q3 screening параллельно. Q3 не зависит от Q2; откладывать единственное новое обучающее вмешательство до окончания всех диагностик не обязательно.
3. Q2 — после уточнения exposure и поведения gate. Q4 — сохранить условной веткой, не расширять до получения информативного state-access результата.
4. После dev выбрать baseline + один метод, выполнить предусмотренные 2 маски × 3 continuation seed. Успех оценивать не только по оптимизируемому контрасту.
5. Только затем внешний DSL и новая редакция текста статьи. Новые компоненты вроде diffusion/VLA не нужны для закрытия найденных вопросов.

Итог: инфраструктура для содержательной статьи стала намного лучше; наступил этап получения и интерпретации реальных модельных результатов, а не дальнейшего расширения числа компонентов.
