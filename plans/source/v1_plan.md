**Тебе стоит взять supervised-обучение, полноту оценки и внешнюю проверку результата. Диме — GRPO, выбор разнообразных обучающих траекторий и расширенный эксперимент с исключёнными парами.** Тогда ваши части дополняют друг друга: он исследует, какие решения попадают в обучение и что происходит при RL, ты — как использовать полученную supervision, сохранить атомарные навыки и проверить устойчивость выводов.

## 1. Сначала закрепить границу с Димой

В последнем абзаце Дима явно выбирает **три направления**. Упоминание им Hit@K, большей модели и обучения на всех правильных программах ещё не означает, что он взял их в работу. Предлагаю закрепить следующее распределение.

| Направление                                  | Исполнитель                         | Что именно входит                                                                                                                |
| -------------------------------------------- | ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| GRPO и его динамика                          | **Дима**                            | Группы all-wrong / mixed / all-correct; accuracy, diversity и coverage по шагам; изменения exploration, novelty и entropy reward |
| Разнообразие обучающих траекторий            | **Дима**                            | Случайный набор против набора с максимальным покрытием пар операций и состояний                                                  |
| Расширение withheld-pairs                    | **Дима**                            | \(k=1,2,3,5\), несколько подмножеств на каждое \(k\), контроль случайного удаления                                               |
| Полные Hit@K, парные различия, стратификация | **Ты**                              | Основная шестизапусковая серия и общий формат анализа                                                                            |
| Replay и забывание                           | **Ты**                              | Доли 0/10/20/40%, каждая операция отдельно, PLAN/APPLY и ошибки формата                                                          |
| Program-only против полной траектории        | **Ты**                              | Одинаковые задачи и программы, различается supervision промежуточных состояний                                                   |
| Обучение на всех правильных программах       | **Ты**                              | Новый supervised objective на фиксированных данных                                                                               |
| Качество верификатора                        | **Ты**                              | Сначала аудит существующего опыта; затем уточнение утверждений либо корректный дополнительный эксперимент                        |
| Другой размер модели                         | **Ты**                              | Повтор основной контрольной пары, не всех экспериментов Димы                                                                     |
| Независимый внешний benchmark                | **Ты**                              | Проверка вне собственного генератора и диагностика domain shift                                                                  |
| Статья и воспроизводимость                   | **Ты**, с проверкой Димой его части | Claims, статусы экспериментов, prompts, manifests, таблицы и приложения                                                          |

**Важная граница:** entropy-регуляризация *твоего supervised loss* и entropy bonus *в GRPO Димы* — разные вмешательства. Первое может входить в твою работу; второе оставляем ему.

Один baseline-checkpoint можно использовать в нескольких сравнениях, если совпадают данные, seed, инициализация и бюджет. Но одинаковую ячейку не нужно обучать дважды под разными названиями.

## 2. Что в приложенном коде существенно меняет план

Здесь есть несколько моментов, которые лучше исправить **до постановки экспериментов**, иначе можно получить результаты, отвечающие не на тот вопрос.

### 2.1. Продолжать нужно основную Stage4-реализацию, а не любой найденный training script

В архиве несколько поколений проекта. Для основной серии статьи ориентир — каталог:

```text
new_stuff/stage4_verifier_bottleneck_audit_v22/source/artifacts/
```

Внутри него нужны:

```text
stage4_composition_confirm_v1_0p6b/code/confirm.py

stage4_distill_v5_0p6b_exploratory_sh1_72p8/code/
    composition_core.py
    composition_model.py
    composition_eval.py
```

Корневой `modcomp/` относится к более ранней среде. А `verifier_bottleneck_codex_pack/src/vbexp/` — реализация второй серии.

Это важно ещё и потому, что **две серии по-разному нормируют вероятности операций**. Основная использует полный словарь со специальными operation tokens, вторая — пять допустимых продолжений. В самой статье отмечено, что это может менять порядок программ. Объединять их результаты как дополнительные реплики одного эксперимента нельзя.  

### 2.2. В context-архиве нет исходных весов и построчных ranking-файлов

Есть код, конфигурации, manifests и сводные результаты, но нет необходимых весов и исходных `.jsonl` с задачами и ранжированиями.

Поэтому первая задача на твоём компьютере — найти и проверить полный архив, frozen tasks, atomic export, adapters и ranking shards. В manifest есть ссылка на `stage4_composition_confirmation_full.zip`, но самого полного архива в приложении нет.

**Для Hit@K не нужно заново обучать модели.** Нужны сохранённые ранги; в худшем случае — повторное оценивание существующих adapters. Из одного Hit@32 полную кривую восстановить нельзя.

### 2.3. Текущий replay добавляет данные, а не заменяет их

В `composition_model.py`, функция `distill_example_specs`, используется:

```python
replay_n = round(len(specs) * replay / (1.0 - replay))
```

Все композиционные примеры сохраняются, атомарные добавляются сверху. Если просто запустить эту функцию с четырьмя долями replay, изменятся одновременно состав данных, количество примеров и число шагов.

**Для предложенного вами эксперимента нужен новый sampler с фиксированным общим объёмом.**

### 2.4. Промежуточные состояния записаны после всей программы

Сейчас target выглядит так:

```text
<OP...> <OP...> <OP...>
TRACE: [state_1] -> [state_2] -> [state_3]
```

Следовательно, сравнение с program-only проверяет **пользу дополнительной supervision на состояниях**. Оно не проверяет, помогает ли уже выписанное промежуточное состояние выбрать следующее действие: при таком формате все действия предсказываются раньше TRACE.

Это не недостаток постановки, но её нужно правильно назвать.

### 2.5. Сохранённые решения не образуют полный correct set

`composition_core.py::exact_shortest_solutions(..., limit=2)` считает общее количество решений, но сохраняет максимум два.

Для обучения на всех правильных программах нельзя взять только сохранённые witness. Нужно перечислить всё пространство нужной длины и построить полную маску правильности.

Кроме того, `composition_eval.py::score_task` работает под `torch.inference_mode()` и преобразует вероятности в Python `float`. Его нельзя непосредственно использовать как differentiable loss.

### 2.6. В опыте с шумом есть несоответствие между реализацией и названием параметра

В `prepare_noisy_verifier_data.py::corrupt` параметр `beta` задаёт вероятность **замены правильного обучающего ответа неправильной программой**.

Это доля испорченной supervision, а не автоматически

$$
\beta=P(\text{accept}\mid\text{incorrect}).
$$

Перед исправлением опубликованного графика нужно сопоставить manifests и установить, этим ли скриптом получены его данные. Но для новых экспериментов эти две величины уже необходимо разделить.

## 4. Пакет U1: полные Hit@K и подробный анализ ошибок

Это первая полезная задача: она непосредственно отвечает Сергею и рецензентам, не требует нового обучения при наличии raw metrics.

### Что реализовать

Для задачи \(x\) сохранить ранг лучшей правильной программы:

$$
R_s(x)=\min_{p\in C(x)}\operatorname{rank}_s(p).
$$

Дальше для каждой реплики и ветви:

$$
H_s(K)=\frac1N\sum_x \mathbf 1\{R_s(x)\le K\},
\qquad K=1,\ldots,125.
$$

Построить две средние кривые — atomic control и composition — и отдельную кривую **парной разности**:

$$
\Delta H_s(K)=H_s^{\mathrm{composition}}(K)
-H_s^{\mathrm{control}}(K).
$$

В существующем `ranking_metrics` уже есть `best_rank`, MRR, correct mass и несколько Hit@K. Поэтому основная реализация здесь — экспорт и агрегирование, а не новый evaluator.

### Что добавить к средним

Стратифицировать ошибки по полю, степени многочлена, глубине программы, числу правильных решений и необходимости SH1. Для последнего различать «SH1 встречается в одном правильном решении» и «SH1 присутствует во всех правильных решениях».

Для каждой задачи записывать изменение ранга, изменение correct mass и переход между состояниями: решили обе ветви / только control / только composition / не решила ни одна.

**Такая парность уже частично присутствует в статье:** Table 9 содержит четыре соответствующих счётчика для каждой реплики. Сначала воспроизвести эту таблицу, затем расширять анализ до отдельных задач и страт. 

### Статистика и проверки

Независимой единицей остаётся training run. Для bootstrap сохранять парность: одинаковые выбранные task IDs для обеих ветвей и выбранных seeds. Это соответствует логике исходного статистического плана. 

Не проводить 125 отдельных тестов с последующим выбором красивого \(K\). Оставить Hit@32 основным endpoint, полную кривую — характеристикой результата, MRR либо площадь под кривой — заранее выбранной дополнительной метрикой.

Обязательные sanity checks: \(H(K)\) не убывает; для разрешимых depth-3 задач \(H(125)=1\); \(H(32)\) совпадает с опубликованным результатом. Для depth 2 использовать максимум 25 кандидатов: Hit@32 там структурно насыщен. 

**Результат пакета:** графики A–D, парные difference curves, построчные изменения, стратифицированная таблица ошибок и воспроизведённые исходные числа.

## 5. Пакет U2: replay 0/10/20/40% и сохранение атомарных навыков

Это не просто подбор гиперпараметра: нужно измерить, какой композиционный выигрыш получается ценой какого ухудшения атомарных навыков.

В основной серии SH1 у composition-ветви заметно хуже, чем у atomic control; общий средний показатель скрывает значительную часть этого эффекта. Поэтому операция должна оставаться отдельным endpoint. 

### Основная матрица

Удобный вариант — фиксировать 5000 предъявлений за эпоху:

| Replay | Композиционные примеры | Атомарные примеры |
| -----: | ---------------------: | ----------------: |
|     0% |                   5000 |                 0 |
|    10% |                   4500 |               500 |
|    20% |                   4000 |              1000 |
|    40% |                   3000 |              2000 |

Если доступно только 4000 уникальных композиционных задач, нужно либо заранее расширить train-only pool, либо уменьшить общий объём. Дополнительные повторы нельзя записывать как новые уникальные задачи.

Композиционные подмножества выбирать обычным заранее заданным случайным способом, желательно вложенными. **Не добавлять сюда maximum-coverage selection — это эксперимент Димы.**

Атомарный replay балансировать по десяти ячейкам: пять операций × PLAN/APPLY.

### Что фиксировать

Начальный checkpoint, tokenizer, prompts, target format, learning rate, LoRA, число предъявлений, epochs, effective batch, optimizer schedule и тестовые задачи.

Исходные настройки — разумная стартовая конфигурация: LoRA rank 32, alpha 64, dropout 0.05, learning rate \(10^{-4}\), две эпохи, effective batch 64. Но новый loader должен действительно читать эти значения из переданного config. 

### Как не запутаться с бюджетом

Основной опыт выше отвечает на вопрос:

> Что происходит при замене части композиционных примеров атомарными при фиксированном числе предъявлений и шагов?

Он **не гарантирует одинакового количества target tokens**, поскольку длины ответов различаются.

Для выбранного на development контраста затем сделать дополнительную проверку при одинаковом target-token budget. В ней число повторов и фактическая доля примеров могут измениться — это нужно измерить и раскрыть.

Не пытаться объявить одновременно одинаковыми уникальные задачи, повторения, target tokens и FLOPs, если реализация этого не обеспечивает.

### Что измерять

На композиционных задачах — H(K), Hit@32, MRR и correct mass. На атомарных — PLAN и APPLY **по каждой операции**, parse rate и semantic accuracy среди корректно распарсенных ответов.

Это разделение необходимо: вторая серия уже показывает случай, когда исчезновение APPLY связано в том числе с потерей требуемого формата ответа. 

Сравнивать одновременно с исходным atomic checkpoint и с отдельным pure-atomic control. Подходящую долю replay выбирать по development как компромисс между composition gain и retention, а не по максимальному Hit@32 на final.

**Минимальный screening:** четыре доли × три seeds = 12 ветвей. Основной pure-atomic control — ещё три, если идентичного готового контроля нет.

## 6. Пакет U3: program-only против supervision промежуточных состояний

Этот опыт непосредственно закрывает вопрос рецензента о том, нужны ли полные траектории или достаточно правильной последовательности операций.

### Нужны не две несопоставимые серии, а три контролируемые ячейки

| Ячейка                      | Ответ модели при обучении | Назначение                                         |
| --------------------------- | ------------------------- | -------------------------------------------------- |
| Full trace                  | Программа + TRACE         | Основная reference                                 |
| Program-only                | Та же программа без TRACE | Те же задачи, witnesses, предъявления и шаги       |
| Program-only, token-matched | Программа без TRACE       | Проверка при сопоставимом объёме обучающих токенов |

Full-trace reference можно взять из U2 с replay 20%, если полностью совпадают конфигурации и manifests.

**Answer-only в PLAN — это последовательность операций.** Это не конечный вектор: target-вектор уже дан модели во входе.

### Что имплементировать

Вынести построение ответа в одну функцию:

```text
render_target(task, witness, format)
```

Сделать fixtures для точного текста и token IDs. До начала TRACE префикс программы должен совпадать между форматами.

Отдельно сохранять число operation tokens, trace tokens и EOS, а также компоненты loss. Для новых сравнений проверить корректную нормировку gradient accumulation: усреднение microbatch means при разных длинах ответов может непреднамеренно менять веса задач.

### Что можно будет заключить

Если program-only сопоставим с full trace, результаты не требуют объяснения через пользу промежуточных состояний. Если full trace выигрывает и при одинаковых предъявлениях, и против token-matched контроля, это более сильное свидетельство пользы дополнительной supervision.

Но ни один из этих исходов сам по себе не доказывает, что модель **использует пошаговые состояния при планировании**: текущий TRACE находится после программы.

**Минимально:** ещё три program-only запуска при использовании готовой full-trace reference; token-matched ячейка — ещё три.

## 7. Пакет U4: обучение на всех правильных программах

Это наиболее содержательный кандидат на новый метод в твоей части. Но здесь важно не заложить в постановку неверное ожидание: **максимизация массы правильного множества сама по себе не гарантирует разнообразия решений.**

### Определить objective через ту же нормированную массу, которую вы измеряете

Пусть \(\mathcal P_d\) — все программы длины \(d\), \(C(x)\) — правильные программы, а \(s_\theta(p\mid x)\) — score программы.

Определим распределение внутри полного пространства кандидатов:

$$
q_\theta(p\mid x)=
\frac{\exp s_\theta(p\mid x)}
{\sum_{u\in\mathcal P_d}\exp s_\theta(u\mid x)}.
$$

Тогда основной новый loss:

$$
\boxed{
\mathcal L_{\mathrm{set}}(x)=
\operatorname{LSE}_{p\in\mathcal P_d}s_\theta(p\mid x)
-
\operatorname{LSE}_{p\in C(x)}s_\theta(p\mid x)
}
$$

Это минус логарифм **candidate-normalized correct-set mass**, а не автоматически вероятность правильного свободного текстового ответа.

### Нужен matched-objective control

Сравнить set loss только с обычным token-level SFT недостаточно: поменяются одновременно correct-set supervision и нормировка objective.

Добавить:

$$
\mathcal L_{\mathrm{single}}(x)=
\operatorname{LSE}_{p\in\mathcal P_d}s_\theta(p\mid x)
-s_\theta(p^\ast\mid x),
$$

где \(p^\ast\) — тот же witness, который используется в program-only SFT.

Минимальная основная пара — **normalized single против normalized set**. Обычный SFT оставить практической reference.

Для прямой проверки разнообразия полезен дополнительный вариант:

$$
\mathcal L_{\mathrm{uniform}}(x)
=
-\frac1{|C(x)|}\sum_{p\in C(x)}\log q_\theta(p\mid x).
$$

Он задаёт равномерную целевую массу на правильных программах, тогда как set loss допускает концентрацию почти всей массы на одной.

### Что реализовать

Нужна differentiable версия scorer, возвращающая tensor scores без `inference_mode`, `float()` и разрывов графа.

Использовать общее дерево префиксов. Для depth 3 это \(1+5+25=31\) различный префикс, а не необходимость независимо прогонять 125 полных последовательностей. Для depth 4 — 156 префиксов.

При этом исходная обучающая смесь содержит depth 2/3/4. Поэтому выбрать один из двух честных вариантов: поддержать полный objective для пространств 25/125/625 либо сделать отдельный depth-3-only эксперимент со **своими заново обученными контролями**.

Не менять глубины обучения только у нового метода.

### Что измерять помимо Hit@32

Нужны correct-set mass и распределение **внутри правильного множества**:

$$
q_\theta(p\mid p\in C(x),x).
$$

По нему считать entropy, эффективное число решений \(e^H\) и максимальную условную вероятность. Основной анализ разнообразия проводить на задачах с \(|C(x)|\ge2\).

Рост общей entropy недостаточен: он может означать рост массы неправильных программ.

### Обязательные тесты loss

При единственном правильном решении set loss должен совпадать с normalized-single по значению и градиенту. Если правильны все кандидаты, normalized set loss должен быть нулевым с нулевым градиентом. Перестановка кандидатов не должна ничего менять; tree scorer должен совпадать с brute-force проверкой.

Также проверить, что correct set не усечён двумя сохранёнными witnesses и не раскрывает запрещённые training motifs через альтернативные решения.

**Минимальная серия:** два normalized objectives × три seeds = шесть запусков. Uniform-correct — ещё три при необходимости. Entropy-регуляризацию добавлять только следующим отдельным шагом, а не одновременно со всеми изменениями.

## 8. Пакет U5: качество верификатора и претензия к two-dial law

Здесь сначала нужно решить, **какой claim вы действительно хотите защищать**.

Рецензент предлагает два допустимых пути: усилить проверку качества верификатора либо сузить формулировку. Не обязательно строить огромную сетку только ради сохранения слова «law». 

### Обязательное действие: разобраться с текущим noise experiment

Для имеющегося скрипта естественное обозначение — \(\rho\), доля неправильных targets в обучающей выборке.

Если же есть настоящий процесс принятия кандидатов, то при доле правильных предложений \(q\):

$$
\rho
=
\frac{\beta(1-q)}
{\alpha q+\beta(1-q)}.
$$

Например, при одном правильном ответе из 125, равномерном предложении кандидатов, \(\alpha=1\) и \(\beta=0.5\), среди принятых будет примерно **98.4% неправильных**, а не 50%.

Поэтому сначала сопоставить script hash → dataset manifest → training run → figure. Если опубликованный опыт получен заменой targets, назвать его **устойчивостью к загрязнению supervision**. Он остаётся полезным, но отвечает на другой вопрос.

### Рекомендуемый основной путь

Не заявлять универсальный two-dial law. Чётко разделить oracle-supervised consolidation, доступность разнообразных кандидатов и конкретные результаты GRPO.

В текущем abstract эти ограничения уже сформулированы существенно осторожнее, чем в критикуемой общей постановке: положительный эффект относится к знакомым семействам композиций, а перенос на withheld motifs не подтверждён. 

### Дополнительный эксперимент — только при необходимости

Для честного verifier-quality опыта сделать замороженный proposal bank и вероятностное принятие по заданным \((\alpha,\beta)\), например:

$$
(1,0),\quad (0.5,0),\quad (1,0.1),\quad
(1,0.5),\quad (0.5,0.5).
$$

Логировать TP/FP/FN/TN, долю принятых, загрязнение accepted set, количество проверок и задачи без принятых кандидатов.

**Gold verifier нельзя затем использовать для удаления принятых неправильных ответов:** это отменит вашу интервенцию.

Для joint quality × exploration проверки использовать два фиксированных candidate banks Димы. Ты реализуешь acceptance и последующее обучение; второй exploration/GRPO sweep у себя не запускаешь.

## 9. Пакет U6: повтор на другой модели

Для сопоставления внутри исходной dense-линейки Qwen3 следующий размер после 0.6B — **1.7B**, затем 4B. Варианты 1.5B/3B из другой линейки не будут чистой проверкой изменения размера. ([Qwen][1])

Начать нужно не с полной серии, а с настоящего training smoke test: загрузка, forward, backward, optimizer step, сохранение и загрузка, затем exact ranking. То, что квантованная модель помещается для inference, ещё не подтверждает работоспособность нужного training pipeline.

Для новой модели нужен собственный atomic checkpoint. Внутри неё сравнить только основную пару: atomic continuation против composition continuation, три paired seeds.

Если 1.7B доступна только в 4-bit, добавить 0.6B bridge в той же конфигурации квантования. Иначе размер будет смешан с численной точностью и способом обучения.

**Не переносить сюда весь план Димы.** Этот пакет проверяет устойчивость основного контраста к размеру модели, а не строит scaling law.

## 10. Пакет U7: независимый внешний benchmark

Это единственная большая претензия, которую нельзя закрыть replay, дополнительными primes или большей моделью. Рецензент отдельно просит real or independently sourced dataset и анализ domain shift. 

Рабочий кандидат — подходящая подвыборка **SyGuS program-synthesis benchmarks**, например PBE/string-задачи. Это внешний источник задач; официальный репозиторий также предупреждает о возможных ошибках и дубликатах, поэтому аудит данных обязателен. ([GitHub][2])

### Сначала проверить осуществимость

До обучения проверить parser, грамматику, interpreter, размер конечного пространства программ и количество задач, которые можно корректно оценить полным перечислением.

Не нужно переделывать исходный benchmark в собственную игрушку из пяти операций ради числа 125. Допустима ограниченная грамматикой подзадача, но с явным описанием ограничений и доли исключённых задач.

### Затем повторить сам экспериментальный принцип

В новой среде подготовить атомарные навыки и сравнить две ветви из одного начального checkpoint: atomic-only continuation и composition supervision.

Нельзя считать неудачу polynomial adapter на незнакомых string operations опровержением механизма: одновременно поменяются смысл действий, формат и распределение задач.

### Как диагностировать domain shift

Оценить одну и ту же пару моделей на внутренних generated tasks **в новой DSL** и на независимых benchmark tasks. По возможности сопоставить сложность: размер программы, число ограничений, количество правильных решений.

Добавить положительный контроль — обучение на разрешённой внешней train-части с оценкой на непересекающемся external test. Если оно помогает, а обучение на внутреннем генераторе — нет, это аргумент в пользу distribution mismatch. Но отрицательный результат сам по себе не устанавливает единственную причину: отдельно проверяются representability, parsing и атомарные навыки.

Для PBE «правильно» означает выполнение заданных input-output constraints. Без дополнительных тестов или reference function нельзя автоматически утверждать корректность на всех входах.

**Если этот пакет не реализован, внешняя валидность остаётся открытым ограничением.** Ещё одна проверка внутри finite-field среды его не заменяет.

## 11. Что изменить в статье независимо от исхода новых опытов

Здесь часть замечаний можно закрыть без новых training runs.

**Развести oracle supervision и self-training.** Основной положительный результат использует программы, найденные exhaustive search. Обучение на всём correct set тоже будет oracle-supervised опытом, а не самостоятельным открытием программ моделью. Источник основной supervision уже описан в статье; это различие нужно выдержать и в framing. 

**Не делать общий вывод «стандартный RL не подходит».** Имеющиеся результаты относятся к конкретному алгоритму, бюджету и расписанию; сама статья это ограничение признаёт. 

**Согласовать статусы экспериментов.** В Appendix E есть важные оговорки о времени amendment и открытии данных. Их нельзя устранить переименованием post-hoc результата в confirmatory. Нужна единая таблица со статусом каждого контраста. 

**Добавить точные prompts и происхождение данных.** PLAN/APPLY/TRACE из реально использованного кода, mapping operation tokens, состав atomic pool по операциям и полям, target masks, seed, package versions, hashes и правила ranking ties.

**Ограничить утверждения о новых комбинациях.** Улучшение ранга, рост correct mass, обнаружение при конечном sampling budget и перенос на никогда не показанные motifs — разные утверждения. Их должны поддерживать разные эксперименты.

## 12. В каком порядке реально делать работу

Я бы запускал не полную декартову сетку всех идей, а четыре последовательные волны.

| Волна | Работа                                                                                                                                              | Новое обучение                                                                  |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| **0** | Ownership, восстановление артефактов, H(K), paired analysis, аудит noise, тесты scorer/budget; параллельно feasibility внешней среды и memory smoke | Для H(K) не требуется при наличии raw metrics                                   |
| **1** | Replay + atomic control + program-only                                                                                                              | Ориентир **18 ветвей** для screening на трёх seeds, до token-matched дополнений |
| **2** | Normalized-single против set-mass; затем при необходимости uniform-correct                                                                          | **6**, опционально ещё **3**                                                    |
| **3** | Большая модель, внешний benchmark, выбранное усиление verifier-quality                                                                              | По результатам предварительных проверок                                         |
| **4** | Подтверждение одного-двух центральных новых выводов                                                                                                 | Отдельная заранее зафиксированная серия                                         |

Три seeds здесь — первоначальная проверка, а не универсальное основание для сильных утверждений. Например, при трёх согласованных ненулевых разностях минимальное двустороннее exact sign-permutation \(p\) равно \(0.25\). Для центрального нового claim разумно заранее назначить шестизапусковую проверку, а не добавлять seeds до появления значимости.

**Первый практический шаг — не запуск обучения.** Закрепить распределение с Димой, найти исходные ranking-артефакты, воспроизвести опубликованный Hit@32 и Table 9, затем сделать новый sampler фиксированного объёма и переключатель `program_only / program_trace`. После этого первые три твоих содержательных пакета — H(K), replay и абляция TRACE — образуют связную серию без дублирования работы Димы.
