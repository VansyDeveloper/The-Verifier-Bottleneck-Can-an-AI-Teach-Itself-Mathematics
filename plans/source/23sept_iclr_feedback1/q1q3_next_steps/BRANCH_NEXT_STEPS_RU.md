## Решение

Не запускать сейчас масштабное подтверждение преимущества CF/энтропии. Продолжать в двух независимых направлениях:

1. Q1: проверить, какая часть различий описывается аддитивными предпочтениями программ, а какая — зависимостью score от условия.
2. Q3: найти режим продолжения, который сохраняет исходные навыки, затем снова сравнить CE и CF на одинаковом режиме.

Q2 может идти отдельно только после восстановления истории нужного checkpoint и прохождения своего численного допуска. Архитектурные изменения, SIGReg и ещё один размер модели не должны задерживать эти две задачи.

Предлагаемая первая настройка, не установленный оптимум:

- четыре composition-задачи в панели;
- дополнительно по одному atomic PLAN и APPLY примеру на panel step;
- коэффициент replay `lambda_replay=0.25`;
- `L_replay = 0.5*(mean-token-CE_PLAN + mean-token-CE_APPLY)`;
- `L_total = L_comp + lambda_replay*L_replay`;
- `L_comp = mean operation CE + lambda_cf*CF - lambda_H*H`.

Это НЕ «20% replay»: число примеров и коэффициент функции потерь — разные величины. Записывать оба, плюс реальные loss-bearing tokens для каждого типа. Если команда предпочитает другой заранее объявленный режим, главное — однозначное определение и одинаковый replay во всех сравниваемых методах.

Replay нельзя включать лишь для CF: выигрыш будет смешивать метод и сохранение навыков. Во всех сравнениях CE/CF/H держать одинаковыми composition tasks, replay tasks, порядок, токены supervision, optimizer steps, initialization и размер panel batch. Прогоны с replay дороже прогонов без него; сравнение наличия replay — диагностическая абляция, а не equal-compute claim.

Заранее определить dev-ограничение удержания: например, падение не больше 5 п.п. на каждой PLAN-операции и на исходно сильных APPLY-операциях. Проверять его полным dev-набором, а не только шумным маленьким монитором. Это инженерный допуск для следующего screening, не новое доказательство успеха v4. Одновременно нужен ненулевой learning progress на train/знакомых композициях, иначе минимальный lr и отсутствие изменений будут тривиально лучшими по retention.

Регрессионные тесты: replay weight=0 оставляет прежний objective; replay не меняет состав/порядок composition panels; data exclusions и поле/операция/mode balance; токены и шаги в budget согласованы; PLAN/APPLY никогда не берутся из dev; две ветви share один replay manifest.

# Коммит 5 — CPU-разложение Q1 и вероятностного сдвига

Файлы: новый `analysis/q1_prior_residual.py`, расширение `research_evaluate.py`/export, отдельный post-hoc report. Не менять primary v4 endpoints.

## 5.1 Crossed nuisance decomposition

Сохранять исходную 4×2 score-матрицу, а не только I/joint. Для d=(d00,d01,d10,d11), где d — score(A)−score(B):

- a=(d00+d01+d10+d11)/4;
- b=(d00+d01−d10−d11)/4;
- c=(d00−d01+d10−d11)/4;
- h=(d00−d01−d10+d11)/4 = I/4.

Чисто аддитивная поправка к предпочтению A относительно B меняет только a. Поэтому strict joint может вырасти при неизменном I. Сохранять: четыре signed margins, minimum margin, I, I>0, параметры a/b/c/h и переходы panel-before/after. Показатель `min(d00,d11)−max(d01,d10)>0` означает, что панель вообще можно исправить единым scalar offset; это диагностическое существование, не готовая test-time correction.

## 5.2 Аддитивная модель изменения score

Выбрать один неизменяемый reference-набор из train/разрешённых A-условий; для самой чистой версии не использовать B/D и новые поля даже для подбора коэффициента. На одних и тех же reference-входах оценить обе группы checkpoints, затем:

`delta_b(z) = mean_reference[s_composition(x,z)-s_control(x,z)]`.

Сравнить на evaluation:

1. raw control;
2. raw composition;
3. control + delta_b;
4. composition − delta_b;
5. task-independent score delta_b (negative control).

Для probability metrics каждую новую score-строку нормировать. Никакого подбора alpha по B/D; начать с заранее заданного alpha=1. Считать joint, I, four-TARGET и ordinary H1/H8/mass. Это проверка конкретной аддитивной модели на уровне program scores, а не доказательство существования отдельного нейронного «модуля prior».

Нужны сырые rankings для панелей/ordinary и reference scores. В compact feedback ZIP их нет; если reference раньше не оценивался, потребуется дополнительный inference, но не новое обучение. После получения scores само разложение выполняется на CPU.

## 5.3 Между пулами или внутри пула

Для B/D и фиксированного диагностического пула F программ с исключёнными парами: pi_i=sum_F q_i, r_i=m_i/pi_i. Тогда m_i=pi_i*r_i. По каждой парной задаче:

`delta_m = (pi_t-pi_c)*(r_t+r_c)/2 + (r_t-r_c)*(pi_t+pi_c)/2`.

Усреднять после разложения, не перемножать средние. Первый член описывает перераспределение массы между пулами, второй — изменение внутри пула. Это точное алгебраическое разложение, НЕ причинная оценка. Restricted ranking использует устройство тестового семейства и не должен становиться основным inference-методом.

Хранить Hit@K и exact IID success `mean[1-(1-m_i)^K]` раздельно. Рост sampled-success при падении Hit@K возможен; нельзя менять search contract статьи задним числом.

# Очередность запусков

## Фаза A: bounded stability screening

Одна и та же mask1, seed0, исходная база и 64 composition panels. Четыре CE-прогона на новой версии кода:

| Run | LR | Replay | Зачем |
|---|---:|---|---|
| R0 | 1e-4 | нет | Повтор исходного CE с кривой по шагам и новой телеметрией |
| R1 | 3e-5 | нет | Изолировать эффект уменьшения LR |
| R2 | 1e-4 | есть | Изолировать replay |
| R3 | 3e-5 | есть | Совместная настройка |

Одинаковый максимум 128 composition updates; snapshots 0/8/16/32/64/128. Значение 3e-5 — предложенная точка bounded pilot, не доказанный оптимум. R0 можно не повторять, если нужны только три probes; тогда старый CE — исторический ориентир, а не полный новый factorial с trajectory и одинаковым code identity.

Не выбирать рецепт по красивому B/D p-value. Выбрать по удержанию навыков и способности действительно обучаться на композициях. Если все рецепты деградируют, не масштабировать CF: разобрать начальные градиенты, данные и objective decomposition. Дополнительный LR допустим только как явно новый dev-шаг, не бесконечный поиск удачного seed.

## Фаза B: повтор метода на устойчивом рецепте

Сравнить CE и CE+CF при одном выбранном LR/replay/общем количестве шагов и одной initialization. Сохранить CF weight=0.1 и tau=1 на первом повторе, чтобы не менять всё одновременно. Новая CE evaluation должна соответствовать checkpoint выбранного общего бюджета. При ресурсе дополнить CE+H и CE+CF+H и сохранить факторную структуру; не объявлять комбинацию победителем по старым +10 п.п. four-TARGET.

Если стабильный CE не хуже CF и ordinary solving не улучшается, фиксировать этот результат. Следующую гипотезу выбирать по diagnostics, а не сразу переходить к 8B/autoencoder.

## Фаза C: ограниченная репликация и final

После выбора одного проверяемого метода — baseline+method, mask1/mask2, paired continuation seeds0/1/2. Одна и та же выбранная длительность для ветвей; не выбирать лучший checkpoint по final или индивидуально по каждому arm. Затем immutable lock и evaluation final без переобучения. Если цель — подтвердить null, нужен отдельный precision/equivalence plan; не считать nonsignificance доказательством отсутствия эффекта.

## Параллельность

На двух GPU: R0/R1, затем R2/R3. На четырёх: четыре R-прогона одновременно. Одновременно CPU восстанавливает историю, проверяет raw atomic ошибки и готовит Q1-диагностику. Освободившаяся GPU делает reference-scoring для Q1 либо диагностическую Q2 с проверенным checkpoint; эти очереди не должны иметь искусственную зависимость от завершения друг друга.

Не изменять код работающих задач. Каждая очередь получает зафиксированный code snapshot, общий manifest, отдельный output, одна GPU на задачу. При оценке промежуточных checkpoint не выдавать незавершённый run за completed.
