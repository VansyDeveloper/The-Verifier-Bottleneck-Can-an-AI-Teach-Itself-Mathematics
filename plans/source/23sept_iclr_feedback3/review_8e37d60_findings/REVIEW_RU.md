## Recovery

`iclr/research_train.py`:

1. `resume_from` безусловно извлекается из config; явный аргумент имеет приоритет.
2. `snapshot_logs` сохраняет byte boundaries и SHA256 трёх журналов; `restore_logs` сначала проверяет ВСЕ committed prefixes, затем обрезает хвосты. Изменённый/короткий/утраченный committed prefix вызывает отказ до мутаций.
3. `complete_checkpoint_receipts` принимает только `step_` с цифровым суффиксом; `.partial/DONE` не становится latest. Явный `.partial` отвергается.
4. Опубликованные checkpoints неизменяемы. Перезапуск на новом snapshot нельзя смешивать с checkpoint 056fd9a без log snapshots.

Это достаточная техническая основа для ограниченного пилота при целостном доступном хранилище; физическая durability или детерминизм между GPU не установлены.

## Реальное ограничение многомашинного запуска

`iclr/research.py:412–435`: `--gpus` принимает локальные индексы; host/SSH/Slurm worker routing нет.
`iclr/upgrade.py:302–307`: единые status.json и эксклюзивный flock `.queue.lock`.
`iclr/upgrade.py:311–318`: незавершённая job с другого host не присваивается автоматически.
`iclr/upgrade.py:355–380`: процессы запускаются локальным subprocess.Popen с cwd=ROOT и CUDA_VISIBLE_DEVICES.

Поэтому:
- Один сервер / четыре GPU: один `research run --gpus 0 1 2 3`, это готовый путь.
- Разные серверы: либо ручное назначение train/eval configs по условиям, либо небольшая будущая надстройка dispatch. Одно и то же условие имеет ровно одного владельца.
- Если скопировать полную очередь на 4 независимых сервера и на каждом выполнить `research run --gpus 0`, получится 16 training jobs вместо четырёх (если все копии выполнятся полностью). Если хранилище общее — второй dispatcher встретит lock, а не подключится к общей работе.
- Прописанные абсолютные пути amendments/base и относительные output paths требуют согласованной структуры каталогов. Не редактировать configs/receipts после начала работы, чтобы искусственно «починить» пути.

## Почему четыре R-условия обоснованы

| Условие | LR | Replay weight | Вопрос |
|---|---:|---:|---|
| R0 | 1e-4 | 0 | Исходная CE-динамика и время деградации |
| R1 | 3e-5 | 0 | Эффект меньшего шага |
| R2 | 1e-4 | .25 | Эффект atomic replay |
| R3 | 3e-5 | .25 | Совместное действие |

Все стартуют от одной фактической базы с ожидаемым hash. Replay/no-replay — не равный compute, и это уже правильно обозначено в плане. Seed0 от одной initialization — пилот, не независимое статистическое подтверждение.

Старый CE endpoint не содержит требуемой новой траектории checkpoint/monitor; поэтому один R0 повтор оправдан. Повторное создание R0 на каждой машине — нет.

## Диагностика не бесплатна

На mask1 один monitor содержит 208 depth3-задач (64 ordinary, 128 crossed B/D cells, 16 TRAIN cells) и 100 atomic tasks, проверяемых в PLAN/APPLY.

4 runs × 6 checkpoints = 24 monitors: 4992 полных depth3 оценивания и 2400 atomic-task evaluations в двух режимах. Само обучение — 2048 composition-task presentations на четыре условия, плюс replay R2/R3.

Каждый full dev: 1856 depth3 задач + 64 depth4 + 1000 atomic tasks в двух режимах, плюс решения выбранных задач. В стандартной очереди full dev выполняется 5 раз: initial и четыре финальных адаптера.

Эти числа НЕ являются отношениями GPU-времени: backward, генерация, длина prompt и kernels имеют разную стоимость. Время A100 не измерено. Но считать «128 шагов — значит всё дёшево» нельзя.

На этой серии сохраняем объявленный monitor/full протокол. Не добавлять full dev для всех 24 checkpoint. Промежуточные full оценки назначать только ограниченному числу кандидатов, выбранных по retention/TRAIN/A, не B/D.

Повторяющийся step0 monitor у четырёх условий — возможный будущий cache, а не повод сейчас менять receipts или останавливать серию. Нужна проверка идентичности payload/data/policy/precision и корректная привязка нового monitor receipt, а не копирование DONE.

## После gate

Retain текущие пороги: <=5 п.п. падения каждой PLAN и исходно сильных APPLY; >=0.001 absolute correct mass gain на TRAIN probe или полном dev A. TRAIN-only PASS означает fitting, не перенос. Сначала выбрать один общий recipe/step; не выбирать длительность отдельно под CE и CF.

Matched CE/CF по существующему плану содержит два запуска. Повтор baseline в этой короткой серии допустим для штатного симметричного пути; это не новый независимый seed. Позже можно реализовать проверяемый reuse идентичного CE checkpoint, но простое переименование старого adapter/receipt неприемлемо. То же касается повторных mask1/seed0 cells в confirmation: не представлять их как новые независимые initialization.

Сейчас не запускать автоматически: entropy sweep, 8B, 256 steps/4 epochs, SIGReg, новую сетку masks/seeds или старую Q3-confirmation. Q2 — отдельная ветка только с verified initialization history и numeric gate; её ожидание не блокирует R0–R3.
