**Да, теперь R0–R3 можно запускать. В проверенной части `8e37d60` новых блокеров для этой ограниченной серии я не нашёл.** Предыдущие проблемы с восстановлением исправлены; ещё раз менять научный план или добавлять методы сейчас не нужно.

**Но есть одно существенное организационное ограничение: несколько GPU одного сервера поддерживаются, а несколько отдельных серверов текущая команда автоматически не объединяет.** Именно здесь можно случайно либо продублировать вычисления, либо получить остановку по блокировке очереди.

Ниже — что запускать, как распределить и где не тратить ресурсы.

## 1. Четыре текущих эксперимента — обоснованы

Сейчас нужно выяснить, удаётся ли продолжать композиционное обучение, не разрушая уже освоенные атомарные навыки. Четыре условия разделяют две причины возможного улучшения:

| Запуск | Learning rate | Atomic replay weight | На какой вопрос отвечает                                        |
| ------ | ------------: | -------------------: | --------------------------------------------------------------- |
| **R0** |        `1e-4` |                  `0` | Как выглядит исходная динамика CE и когда начинается деградация |
| **R1** |        `3e-5` |                  `0` | Достаточно ли уменьшить шаг обучения                            |
| **R2** |        `1e-4` |               `0.25` | Помогает ли сохранение атомарных навыков через replay           |
| **R3** |        `3e-5` |               `0.25` | Помогает ли сочетание меньшего шага и replay                    |

У всех — одна фактическая база, `mask1`, `seed0`, 64 панели и максимум 128 обновлений. **Это не четыре случайные вариации: каждый запуск нужен для интерпретации остальных.**

Повтор R0 оправдан: старый конечный результат не даёт новой требуемой динамики по checkpoint. Но **повторять R0 отдельно на каждой машине уже незачем**.

Я построил очередь на полных данных. Она действительно содержит **10 заданий: импорт данных, одну initial full-dev оценку, четыре обучения и четыре full-dev оценки конечных адаптеров**. Никакие дополнительные модели или сетки параметров скрыто не запускаются. [Проверенная структура очереди](review_8e37d60_findings/queue_inventory.json).

## 2. Где сейчас действительно можно потратить лишнее

### Полная очередь на каждой машине — главный риск

Команда:

```bash
uv run python -m iclr.research run \
  --queue outputs/v5_stability_feedback2/queue.json \
  --gpus 0 1 2 3
```

означает **четыре локальные GPU одного сервера**.

Она не означает «найти четыре A100 на разных компьютерах». В коде используются локальные процессы, единый `status.json` и эксклюзивная блокировка `.queue.lock`. Незавершённый процесс с другого host также не подхватывается автоматически.

Поэтому:

**Если скопировать полную очередь на четыре независимых сервера и на каждом выполнить `research run --gpus 0`, получится до 16 обучений вместо четырёх.** Если запускать несколько диспетчеров на общей файловой системе, второй встретит блокировку, а не присоединится к работе.

Это не дефект обучения. Это отсутствие распределённого диспетчера, которое README пока недостаточно явно объясняет. [Разбор соответствующих участков кода](review_8e37d60_findings/REVIEW_RU.md).

### Диагностика уже достаточно объёмная — расширять её не надо

На один checkpoint ваш monitor оценивает **208 композиционных задач и 100 атомарных задач в PLAN/APPLY**. На четыре условия и шесть checkpoint получается **24 monitor-запуска и 4992 оценивания композиционных задач**, помимо full dev. Это расчёт по приложенным manifests. [Проверка объёмов](review_8e37d60_findings/CHECKS.json).

Это не соотношение GPU-времени: обучение с backward, ранжирование и генерация имеют разную стоимость. Но «всего 128 шагов» не означает, что вся очередь почти бесплатна.

**В этой серии я бы сохранил уже зафиксированный monitor. Но не добавлял full dev для всех 24 checkpoint.** Полная оценка уже предусмотрена для initial и четырёх конечных адаптеров. Для промежуточных шагов она нужна только выбранным кандидатам.

Повторяющийся step-0 monitor у четырёх условий можно впоследствии кэшировать с корректной привязкой к весам и данным. Сейчас это не повод ещё раз переписывать trainer и откладывать четыре запуска.

## 3. Как распределить на разных A100

### Сначала — общая подготовка, один раз

Один координатор фиксирует код, данные, amendments, model profile и очередь. На одном устройстве выполняется **initial full dev**. Затем эти общие результаты и конфиги становятся доступны остальным workers.

После этого четыре обучения независимы:

| Устройство  | Обучение | После его завершения |
| ----------- | -------- | -------------------- |
| **A100 №1** | R0       | Full dev своего R0   |
| **A100 №2** | R1       | Full dev своего R1   |
| **A100 №3** | R2       | Full dev своего R2   |
| **A100 №4** | R3       | Full dev своего R3   |

**Каждое условие стартует из общей initialization, а не из результата другого условия.** Объединять эти карты через DDP для одного обучения не требуется.

На двух устройствах: первое выполняет R0, затем R2; второе — R1, затем R3. На одном сервере штатный планировщик может перемежать готовые train/eval задания — это нормально.

### Когда все карты находятся в одном сервере

Оставляйте текущий штатный путь: **одна очередь, один dispatcher**, `--gpus 0 1 2 3`. Для двух карт — `--gpus 0 1`.

На старте остальные карты могут ждать initial evaluation: такая зависимость действительно заложена в очереди. Не нужно заполнять это короткое ожидание новыми научными экспериментами.

### Когда A100 находятся на разных серверах

**Назначайте каждому серверу конкретный train config и соответствующий eval config.** Уже существующие worker-модули это позволяют; новый training framework не нужен.

Например, серверу с R2 после общей подготовки:

```bash
export CUDA_VISIBLE_DEVICES=0
export OMP_NUM_THREADS=4

uv run python -m iclr.research_train \
  --config outputs/v5_stability_feedback2/configs/q06_mask1_R2_seed0_train.json

uv run python -m iclr.research_evaluate \
  --config outputs/v5_stability_feedback2/configs/q06_mask1_R2_seed0_eval.json
```

На других серверах меняется только назначенное условие: R0, R1 или R3. **Полный `research run` на каждом worker при такой схеме не запускается.**

Здесь обязательны три условия:

* **Одинаковые входы и настройки:** код, реальные веса базы, manifests, tokenizer, precision, зависимости и `prefix_batch`. На A100 не надо самовольно увеличивать `panel_batch` или менять learning rate.
* **Согласованные пути:** в configs есть абсолютные пути. Нужны одинаковые каталоги или mount points; нельзя после обучения исправлять пути редактированием receipts.
* **Один владелец каждого задания:** один и тот же config не запускают одновременно два человека. Прямой worker entrypoint не заменяет распределённую блокировку.

Я подготовил [**инструкцию для одного сервера и нескольких отдельных A100**](sandbox:/mnt/data/review_8e37d60_findings/A100_RUNBOOK_RU.md): подготовка, common initial, команды каждого worker, сбор результатов и проверка, что все задания действительно завершены. Она использует существующие команды проекта, а не вымышленные флаги `--host` или `--condition`.

## 4. Что обязательно сохранить с каждого устройства

**Возвращать нужно целиком каталог обучения и каталог оценки своего условия, а не только таблицы метрик.**

В частности, должны сохраниться промежуточные adapters, `resume_state.pt`, журналы, manifests и `DONE`. Иначе вы увидите хороший monitor на шаге 16, но не сможете выполнить full dev именно этих весов или продолжить прерванный run.

**Weight-free feedback ZIP — не резервная копия эксперимента.** Он подходит для части анализа, но не заменяет хранилище checkpoint.

Общий `status.json` должен оставаться под управлением координатора. В инструкции отдельно расписан сбор без перезаписи receipts и проверка всех десяти результатов перед согласованием master-очереди.

## 5. Что запускать после этой серии — и что не запускать

Следующий шаг зависит от результатов, а не от количества свободных GPU.

### После R0–R3 — выбрать один устойчивый режим

Сохраняйте текущие правила: допустимое падение по каждой PLAN-операции и исходно сильным APPLY-операциям — не более 5 п.п.; нужен прирост correct mass не менее `0.001` на фиксированном TRAIN probe **или** полном dev A.

**Monitor помогает выбрать кандидата, но не заменяет full-dev допуск.** Проход только по TRAIN означает обучение примерам, а не установленный перенос.

Режим и число шагов выбираются по retention/TRAIN/A, не по удобному результату B/D. При нескольких подходящих вариантах — предусмотренное предпочтение меньшего числа шагов, затем меньшей стоимости replay.

### После успешного допуска — только matched CE против CE+CF

Один общий LR, replay, число шагов, initialization и порядок данных. На двух A100 — по одному условию на карту. Atomic skills после CF проверяются заново: успешный CE не гарантирует, что CF их сохранит.

**Не добавляйте автоматически энтропию, SIGReg и 8B только потому, что осталось ещё две карты.** Свободное устройство дешевле, чем незапланированный эксперимент с неясной интерпретацией.

Если ни один режим не проходит допуск, масштабирование CF останавливается. Тогда сначала разбирается уже сохранённая динамика — без ослабления порогов и автоматического удвоения эпох.

Q2 может идти отдельной веткой, но только при проверенной истории именно её initialization и пройденном численном допуске. Её ожидание не должно задерживать R0–R3.

## 6. Что сейчас изменить в ветке

**Для запуска на одном сервере обязательных изменений научного кода я не вижу.** Для нескольких серверов я бы сейчас дополнил документацию:

**Явная таблица «устройство → условие → train config → eval config», один общий initial, запрет запускать полную очередь на каждом worker и порядок сбора результатов.** Готовый runbook по ссылке выше закрывает именно это.

Дальше полезно отдельно учитывать время обучения, monitor, full evaluation и повторных попыток после прерывания. Сейчас elapsed trainer включает monitor и начинается заново после resume, поэтому его нельзя без поправок выдавать за полные GPU-hours эксперимента. Но добавление красивого профилирования не должно стать новым обязательным этапом перед R0–R3.

### Границы моей проверки

Самостоятельно проверены размеры и хеши **378 файлов**, пройдены **28 доступных CPU-тестов** и **8 изолированных сценариев config/recovery без загрузки модели**; построена полная очередь. Архивные CUDA-регрессии прочитаны, но здесь не повторены. Веса отсутствуют; обучение, время работы A100 и детерминизм между разными устройствами я не измерял.

**Итог: текущая научная очередь адекватная. Главная задача сейчас — правильно раздать четыре условия, а не расширять их число. На одном сервере запускайте штатный dispatcher; на разных серверах — конкретные назначенные jobs с последующим сбором.**
