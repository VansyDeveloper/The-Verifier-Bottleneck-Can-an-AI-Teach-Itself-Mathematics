# Распределение работы к ICLR

Основание: переписка команды 3–10 сентября 2026 года, отправленная статья и три рецензии. Команды запуска — в [корневом README](../README.md).

| Кто | Что делает |
|---|---|
| Дима | GRPO: неверные/смешанные/верные группы, динамика точности и покрытия, изменения exploration/reward. Выбор разнообразных обучающих траекторий. Исключение 1/2/3/5 пар операций с несколькими наборами пар. |
| Артём | H(K), парный анализ и группы ошибок; replay и забывание; программа без TRACE; обучение на всех правильных программах; повтор основной пары на другой модели; правки статьи. |
| Андрей | Запускает подготовленные конфигурации, сохраняет результаты, время и память. |

В очереди Артёма нет GRPO, выбора траекторий по разнообразию и перебора исключённых пар. Baseline и одинаковая ветвь r=20%/TRACE используются повторно. Смена названия эксперимента не создаёт новую независимую реплику.

## Что именно запускает эта ветка

Это новый протокол продолжения Stage4. Исторические исходники и опубликованные результаты сохранены отдельно.

| Очередь `--recipe` | Сравнение |
|---|---|
| `replay` | 0/10/20/40% атомарных примеров при одинаковом числе предъявлений и шагов. Атомарные примеры заменяют композиционные. Дополнительно: чисто атомарный контроль к r=20%/TRACE по числу обучающих токенов. |
| `trace` | Та же r=20% выборка: программа с TRACE и без него. Третья ячейка: программа без TRACE с контролем числа обучающих токенов. |
| `set` | Отдельная серия только на глубине 3, без replay: обычный program-only SFT, normalized-single и set-mass по всем 125 программам. Все три контроля обучаются на этой постановке заново. |
| `size` | Чисто атомарное продолжение и r=20%/TRACE для указанной модели. Для Qwen3-1.7B нужен собственный атомарный checkpoint. |

По умолчанию: три training seed, две эпохи, effective batch 64. Новые данные: 5000 композиционных задач с глубинами 2/3/4 в пропорции 1:2:1; отдельно development и final A–D. Размер каждого A–D набора по умолчанию 200 задач. Это не исторические final-наборы.

Сохранены пять операций, исходные поля и три исключённые пары. Атомарный replay сбалансирован по PLAN/APPLY × операция. Генератор исключает пересечения состояний всех правильных траекторий между задачами; полный correct set не обрезается до двух witness.

Число предъявлений, обучающих токенов и вычислительные затраты — разные бюджеты. В token-budget ячейках меняется число предъявлений; фактические величины сохраняются в receipt. Новое обучение не следует считать буквальным воспроизведением старого trainer.

Три seed — первичная проверка гипотез. Для выбранного нового подтверждающего результата нужны заранее зафиксированные final-набор, число запусков и правило остановки. Параметры выбираются на development.

## Что известно по основной серии

Из `evidence/PRIMARY_ANALYSIS.json` повторно проверены все строки Table 9 и арифметика основного результата: 45,32% → 72,72% Hit@32; разность 27,40 п.п.; exact sign-flip p=0,03125. Это проверка сохранённых агрегатов.

В этой ветке нет исходных adapters, frozen task files и построчных рангов основной шестизапусковой серии. Нужен полный архив `stage4_composition_confirmation_full.zip` либо эти файлы отдельно с проверяемыми manifests. Полную историческую H(K) из агрегатов восстановить нельзя.

Для локальной второй серии H(K) уже построена по найденным рангам: три пары, 300 задач на знакомых и 300 на новых полях. [Исходные данные и проверка](../evidence/local_series/README.md). С основной серией она не объединяется.

`iclr.analyze` принимает реальные task-level metrics: считает все K, парные различия, интервалы по training runs и ошибки по полю, степени, числу решений и необходимости SH1. Метрики разных scorer/tokenizer/prompt в одном сравнении отклоняются. При отсутствии нужных task-полей группа помечается `unknown`.

## Ответы на рецензии

- Несколько K и парность: новый анализ готов к построчным данным; старая полная H(K) ждёт исходных файлов.
- Забывание: replay-серия; PLAN и APPLY каждой операции, SH1 отдельной строкой, ошибки формата отдельно от выполнения.
- Польза промежуточных состояний: trace-серия. TRACE записан после программы, поэтому опыт не доказывает использование состояния при выборе следующего действия.
- Все правильные решения: set-серия. Рост их суммарной массы сам по себе не доказывает сохранение разнообразия.
- Одна модель: повтор основной пары на 1.7B. Время и память определяются пробным запуском; 4B/9B не включены в обязательную очередь.
- Verifier noise: старый скрипт меняет правильные targets на неправильные. Связь с Figure 9 надо подтвердить по manifests; доля испорченных targets не равна условной вероятности false accept. Новый sweep не назначен.
- Формулировки статьи: разделить обучение на решениях exhaustive oracle и самостоятельный поиск решений моделью. Ограничить вывод о GRPO проверенным алгоритмом и бюджетом; универсальный two-dial law не установлен.
- Статусы второй серии: сохранить различие preregistration, раскрытого amendment и post-hoc анализа; уточнить противоречивую подпись Table 11.
- Внешняя проверка: отдельный benchmark команда ещё не выбрала. SyGuS и новая DSL не реализуются в этой очереди; внешняя валидность остаётся открытой.

Отрицательные результаты и неудачные запуски сохраняются. Новые числа в статью добавляются после завершённых расчётов и проверки их источников.
